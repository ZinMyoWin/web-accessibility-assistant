# Code quality and risk audit

This is a source-based review of selected high-impact flows, not a penetration test or a complete audit of every function. The assumed deployment is an internet-facing application with authenticated users, a PostgreSQL database, and one or more scan workers. Findings describe conditions visible in code; live configuration and exploitability have not been verified. They are recommendations, not changes made by this audit.

## High priority

1. **Some axe findings are discarded without an equivalent custom finding.** [`merge_issues`](../../backend/app/services/axe_scanner.py) drops every axe rule listed in its overlap map, even when the corresponding custom issue is absent. For example, the map includes `html-lang-valid`, whereas the custom check in [page_scanner.py](../../backend/app/services/page_scanner.py) only reports a missing language. A direct call with an `html-lang-valid` axe issue and no custom issues returned an empty list. This can hide accessibility findings. Characterize overlapping rules and individual element matches, then keep unmatched axe findings with regression tests; changing this alters scan results and is not a behavior-preserving refactor.

2. **Scan requests can reach private addresses before a redirect is rejected.** [URL validation](../../backend/app/utils/url_utils.py) permits private targets by default. Even with strict checking enabled, [browser navigation](../../backend/app/services/page_scanner.py) calls `page.goto` and waits before validating the final URL; the raw HTML path also follows redirects before returning the final URL. A public page can cause requests to a private destination or load private subresources before that later check. Enforce network egress restrictions for the scanner and design request-by-request redirect/subresource protection; test that forbidden destinations are never contacted, including DNS rebinding. A final URL check alone is not an isolation boundary.

3. **Docker build context can include local frontend environment files.** [Frontend Dockerfile](../../frontend/Dockerfile) copies the build context into the image, but [frontend ignore rules](../../frontend/.dockerignore) do not exclude environment files. If one exists in that context, it can be copied into a build layer and the resulting image. Exclude these files and verify intended build-time configuration before rebuilding; assess whether existing images need replacement and credentials need rotation. No environment file was opened in this review.

4. **Compose does not pass through two security settings used by the code.** Neither [production-style](../../docker-compose.yml) nor [development](../../docker-compose.dev.yml) Compose config passes `ENCRYPTION_KEY` or `SCAN_ALLOW_PRIVATE_TARGETS` to backend/worker services. [Encryption](../../backend/app/utils/encryption.py) falls back to a known development key, including when a supplied key is invalid; [target validation](../../backend/app/utils/url_utils.py) permits private targets by default. Merely setting a host variable does not pass it into these containers without a service mapping or override. Plan secure configuration and key rotation carefully: switching keys can make existing stored provider keys unreadable. Also address the redirect and subrequest risk above; strict URL validation alone is insufficient.

5. **Reset tokens are not consumed atomically with the password change.** [Reset handler](../../backend/app/main.py) reads a valid token and invokes password update followed by token invalidation. Both [repository operations](../../backend/app/repositories/auth_repository.py) commit separately. Two concurrent requests can both pass the initial lookup, and a failure between commits can leave the token usable. Characterize with concurrency tests against PostgreSQL, then consume the token and update the password in one transaction with appropriate locking or an atomic conditional update. Separately, reset email delivery is not implemented, although the response says a link has been sent.

6. **A recovered scan can still be updated by its previous worker.** [Recovery and completion](../../backend/app/repositories/scan_repository.py) requeue stale work but completion updates by scan ID without checking the current worker or attempt. If a slow worker resumes after another worker reclaims the job, both may write results or terminal status. Add attempt/ownership fencing across progress, failure, cancellation and completion, backed by multi-worker PostgreSQL tests. Do not infer safety merely from row locking during the initial claim.

## Functional and maintenance risks

7. **Opening an older scan can display a different scan.** [Issues page](../../frontend/src/app/(dashboard)/issues/page.tsx) loads the first 50 summaries and accepts the requested ID only if it is in that set; [history](../../frontend/src/app/(dashboard)/scan-history/page.tsx) links arbitrary pages to it. With more than 50 scans, a valid older selection can fall back to the newest scan. Fetch the requested ID directly and surface a real access/not-found error; add a regression test.

8. **History sorting and comparison can mislead.** [History](../../frontend/src/app/(dashboard)/scan-history/page.tsx) fetches ten rows and sorts only those rows, so oldest/most/fewest do not order the whole result set. [Comparison](../../frontend/src/components/scan-history/ScanHistoryCompareView.tsx) keys issues without page URL and stores them in a map, collapsing matching rule/locator/text combinations across pages. Define the intended cross-page sort and issue identity, then test paginated and multi-page examples before changing behavior.

9. **Logout can fail to clear the local session during a network failure.** [Auth context](../../frontend/src/lib/contexts/AuthContext.tsx) waits for the backend logout request before signing out from Auth.js; [logout](../../frontend/src/lib/auth.ts) propagates a network rejection. If the API is unreachable, local sign-out is skipped. Test this case and decide how to clear the local session while communicating that server-side revocation may not have succeeded.

10. **The crawl's initial URL is scanned before the robots check.** [Scanner](../../backend/app/services/page_scanner.py) scans the starting page before it evaluates robots rules for later queued candidates. When `respect_robots_txt` is enabled, a disallowed initial path can still be fetched. Clarify the intended policy and add a regression test before altering it.

11. **Automated checks leave a live integration gap.** [CI](../../.github/workflows/quality-gate.yml) runs unit/API checks and a browser suite, but [browser configuration](../../frontend/playwright.config.ts) documents mocked backend requests; CI does not start PostgreSQL or run migrations. Add a seeded PostgreSQL and worker integration path when infrastructure permits, especially for the password-reset and worker-recovery findings. Existing checks remain useful but cannot establish the complete deployed flow.

12. **Worker mode replaces a requested zero crawl delay with 250 ms.** [Request validation](../../backend/app/schemas/scan.py) permits `request_delay_ms=0`, and [settings resolution](../../backend/app/services/scan_options_resolver.py) preserves it. However, the [worker's payload reconstruction](../../backend/app/scan_worker.py) uses a truthiness fallback, converting zero to 250. Background and worker execution therefore differ. Add a worker-mode regression test before changing the fallback.

13. **The report always labels the scan WCAG 2.1 AA.** [Report mapping](../../frontend/src/lib/saved-scans.ts) sets this label to a fixed string, while scan settings can select a different standard. A report can therefore present a standard that was not used for that scan. Trace how the chosen standard is persisted and exposed, then add an accurate label and regression tests or explicitly show that the standard is unknown for older records.

14. **The API metrics endpoint does not show all worker counters.** [Metrics](../../backend/app/services/metrics.py) stores scan completion and issue counters in each process. The separate worker records its own values, while [the HTTP endpoint](../../backend/app/main.py) exposes the API process's registry; scraping only that API misses worker-local counters. Its database-backed queue and attempt gauges are global, so summing identical gauges from multiple API instances can instead double-count. Define an aggregation strategy and verify it with more than one process. The enabled endpoint also lacks authentication, so restrict access at the deployment boundary if aggregate operational data should not be public.

15. **Benchmark tools can report misleading conclusions or iteration counts.** [Fallback checker](../../scripts/perf/check_fallback_path.py) writes a predetermined conclusion about an old undefined-variable defect, but the current [scanner](../../backend/app/services/page_scanner.py) passes explicit WCAG arguments to its fallback analysis. Its fixed text is not evidence of what a new run observed. [Scan benchmark](../../scripts/perf/bench_scan.py) accepts `--iterations`, but outside quick mode uses each scenario's built-in count instead. Revise these tools and add focused checks before relying on new output; historical benchmark JSON is not a measurement of the current implementation.

## Review boundaries

These findings were checked against source but not reproduced in a live deployment. No changes to contracts, database schema, secret values or user data were made for this audit. Coverage of every helper, UI control, dependency, external service and concurrency scenario is still pending; see [progress](../PROGRESS.md).
